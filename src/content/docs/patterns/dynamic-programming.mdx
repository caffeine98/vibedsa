## What it is

Dynamic programming (DP) solves a problem by breaking it into smaller versions of itself. It solves each smaller problem **once**, saves the answer, and reuses it.

It helps when a problem has two traits:

- **Overlapping subproblems:** the same smaller problem comes up again and again. Plain [recursion](../../foundations/recursion/) would solve it each time.
- **Optimal substructure:** the best answer is built from the best answers to smaller problems.

This page covers the idea, using one-dimensional problems. [Part 2](../dynamic-programming-2d/) covers problems that need a 2D table.

## How it works

### Climbing stairs

You can climb 1 or 2 stairs at a time. How many ways are there to climb `n` stairs?

Look at the **last** step. It was either 1 stair (from stair `n − 1`) or 2 stairs (from stair `n − 2`). So:

```text
ways(n) = ways(n − 1) + ways(n − 2),   with ways(0) = ways(1) = 1
```

Written as plain recursion, this is the [Fibonacci call tree](../../foundations/recursion/#repeated-work). It repeats work and costs O(2ⁿ). DP removes the repeats in one of two ways.

**Top-down (memoization):** keep the recursion, but cache each answer. The first call for `ways(5)` computes it. Every later call just looks it up. In Python, `@functools.cache` does this for you.

**Bottom-up (tabulation):** skip recursion. Fill a table from the smallest case upward, so every answer you need is already there:

<div class="vd-trace">

| n | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ways | 1 | 1 | 2 | 3 | 5 | 8 | 13 |

</div>

Each entry is the sum of the two before it. Both versions are O(n).

### Fewest coins

Pay amount 6 with coins 1, 3 and 4, using as few coins as possible. ([Greedy](../greedy/) gets this wrong.)

Again, look at the last coin. If it was coin `c`, the rest is the best way to pay `a − c`. Try every coin and keep the best:

```text
best(a) = 1 + min( best(a − c) for each coin c ≤ a ),   with best(0) = 0
```

<div class="vd-trace">

| a | last coin 1 | last coin 3 | last coin 4 | best(a) |
| --- | --- | --- | --- | --- |
| 0 | – | – | – | 0 |
| 1 | 1 + best(0) = 1 | – | – | 1 |
| 2 | 1 + best(1) = 2 | – | – | 2 |
| 3 | 1 + best(2) = 3 | 1 + best(0) = 1 | – | 1 |
| 4 | 1 + best(3) = 2 | 1 + best(1) = 2 | 1 + best(0) = 1 | 1 |
| 5 | 1 + best(4) = 2 | 1 + best(2) = 3 | 1 + best(1) = 2 | 2 |
| 6 | 1 + best(5) = 3 | 1 + best(3) = 2 | 1 + best(2) = 3 | 2 |

</div>

The answer is 2 (3 + 3).

### The recipe

1. **Define the state.** What does one entry mean? Here: "`best[a]` = fewest coins to pay `a`".
2. **Write the recurrence.** How does an entry come from smaller ones? Thinking about the *last* choice usually works.
3. **Set the base cases.** The entries you know without any work, like `best[0] = 0`.
4. **Pick an order.** Fill entries so that everything an entry needs is already done.
5. **Read off the answer.** Usually the last entry.

## Pseudocode

```text title="Pseudocode"
CLIMB-STAIRS(n):
    ways = array of n + 1 ones          // ways[0] = ways[1] = 1
    for i from 2 to n:
        ways[i] = ways[i - 1] + ways[i - 2]
    return ways[n]

MIN-COINS(coins, amount):
    best = [0] followed by amount copies of infinity
    for a from 1 to amount:
        for each coin c:
            if c <= a and best[a - c] + 1 < best[a]:
                best[a] = best[a - c] + 1
    return best[amount]                 // infinity means impossible
```

## Complexity

| Function | Time | Space | Why |
| --- | --- | --- | --- |
| Climbing stairs (either version) | O(n) | O(n) | Each of the `n` entries is computed once, from two others. |
| `min_coins` | O(amount · c) | O(amount) | Each amount tries each of the `c` coins. |

The general rule: **time = number of states × work per state**.

Climbing stairs only ever looks two entries back. Keeping just two variables instead of the whole table cuts its space to O(1).

## Gotchas

- **Memoization still recurses.** Top-down DP on a big `n` can hit Python's recursion limit. Bottom-up avoids that.
- **Base cases are easy to get wrong.** Check the smallest inputs by hand: `ways(0)`, `best(0)`, an amount no coin can reach.
- **Mark "impossible" clearly.** Use infinity or `None`, not 0. Otherwise an impossible amount looks like it needs no coins.
- **`@cache` needs hashable arguments.** Pass tuples, not lists, into a cached function.

## In practice

- Suspect DP when a problem asks for a **count** of ways, or the **best** (min or max) result, and its choices build on each other: paths, splits, sequences.
- Start with the plain recursive solution. If it solves the same calls repeatedly, add `@functools.cache`. If it's still too slow or too deep, turn it into a table.
